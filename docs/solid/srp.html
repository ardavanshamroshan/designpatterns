SOLID · S

Single Responsibility Principle

Also known as: Separation of Concerns (related idea)

Intent

A class should have one primary reason to change. Put different kinds of work in different places.

Responsibility ≈ a reason the class would need to change — not “number of methods.”

Problem

You start a simple Journal: add entries, remove them, print them. Then someone asks to save to disk. You add save() and maybe load() on the same class.

Now the class changes when entry rules change and when file format or I/O changes. Two reasons. Testing gets harder. Reuse gets messier.

Solution

Keep Journal focused on entries. Move persistence to a separate collaborator — here, PersistenceManager.

entries
→
PersistenceManager
file I/O
→
journal.txt

That second class is the fix, not the violation.

Compare code

Toggle violation vs the repo’s compliant example.

# Two reasons to change in one class
class Journal:
    def add_entry(self, text): ...
    def remove_entry(self, index): ...

    def save(self, filename):  # persistence mixed in
        with open(filename, "w") as f:
            f.write(str(self))
# From solid/single_responsibility/main.py
class Journal:
    def add_entry(self, text): ...
    def remove_entry(self, index): ...
    # no save / load here

class PersistenceManager:
    @staticmethod
    def save_to_file(journal, filename):
        with open(filename, "w") as f:
            f.write(str(journal))

Structure

Class Responsibility Methods
Journal Manage diary entries add_entry, remove_entry, __str__
PersistenceManager Write a journal to disk save_to_file

Walkthrough

Open each step when you’re ready.

add_entry stores numbered lines. Printing the journal joins them with newlines — still pure domain logic.

save_to_file(journal, path) only knows how to open a file and write str(journal). Swap file for network later without touching Journal.

The demo writes journal.txt next to main.py and prints its contents — proof the split works.

Takeaway

  • Domain object → business data and behavior
  • Persistence helper → how that data is stored
  • Mixing them couples your model to the filesystem
